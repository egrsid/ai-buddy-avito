# Ручная приёмка AI-buddy v3

Стенд: http://localhost:15174. Данные синтетические. Выберите «Live API» — это
настоящий Go/БД, а не платная LLM. Ответы LLM сейчас offline и так помечены.
Не отправляйте сообщения по вымышленным Telegram-контактам.

## Перед проверкой

Запуск из корня ветки `feature/local-v3-integration` на подготовленном ноутбуке:

```sh
DEMO_FRONTEND_PORT=15174 DEMO_BACKEND_PORT=18081 python3 -m scripts.demo up --offline --project ai-buddy-demo-v3
```

Нужен запущенный Docker. `--offline` требует dependency images, уже подготовленные
на этом ноутбуке; на новой машине используйте обычный `up` без `--offline` при доступной сети.
Не выполняйте reset/down --volumes: это удаляет прогресс. Для чистой приёмки используйте
новый project `ai-buddy-demo-qa-ИМЯ` и свободные порты. Не тестируйте в двух вкладках
под одним аккаунтом одновременно: новый вход закрывает предыдущую сессию.

«Мои цели» — технические маршруты с автоматически проверяемыми подзадачами.
«ТЗ от наставника» — назначенные описания результата, требований и критериев приёмки;
отметка неясности здесь не означает выполнение цели. Наставник управляет ТЗ в «Мои задания».

## Участники

Основные роли выбираются в «Демо-аккаунт»: стажёр intern-a, наставник buddy-a,
согласующий approver-a, владелец документации docs-owner-a.
Включите «Дополнительные участники»: intern-b и шесть новых стажёров intern-d…intern-i
команды A; intern-c и buddy-b — чужая команда для проверки запретов.
Новые стажёры первоначально без прогресса: действия выполняйте через UI, статистика
появится из настоящих проверок и отметок, а не выдуманных результатов.

## 1. Цели, подзадачи и доступ к БД

1. Под intern-a откройте «Мои цели». При первом запуске начните разрешённый маршрут.
   Все существующие разные маршруты отображаются сразу, каждый отдельной карточкой.
2. Раскройте подзадачи клавишей Enter или мышью; откройте «Проверить доступ».
3. При отсутствии доступа подготовьте заявку (в чате или кнопкой «Запросить доступ»).
   Проверьте ресурс/роль/основание в preview. До «Подтвердить» заявки быть не должно.
4. Подтвердите. В «Мои заявки» — отправлено, но это ещё не выданный доступ.
5. Переключитесь на согласующего. Одобрите заявку с основанием. Для отдельной заявки
   другого стажёра проверьте отклонение. Стажёр не может одобрить собственный запрос.
6. Вернитесь к стажёру, повторите проверку доступа. Только IAM-проверка меняет прогресс.
7. Откройте «Проверить подключение». SSL disable → DB_SSL_REQUIRED и блокер.
   SSL require после выдачи доступа → passed, блокер устранён, прогресс 100%.
8. Вернитесь к целям: поздравление о выполнении всех текущих задач. Повторно начинать
   тот же маршрут не предлагается. Старые репетиции не создают повторные карточки маршрута.
9. Обновите страницу: verified сохраняется. Если есть несколько разных целей,
   проверьте независимое раскрытие каждой и правильный прогресс конкретного маршрута.

## 2. ТЗ: создание, публикация и назначение

1. Наставник → «Мои задания» → «Новое ТЗ». Заполните название, цель, раздел,
   ожидаемый результат и критерии. Сохраните черновик.
2. Убедитесь, что стажёр черновик не видит. Опубликуйте версию 1.
3. В «Кому назначить» выберите intern-a и нажмите «Назначить», затем intern-b.
   Оба отображаются в «Назначениях».
4. Повторно назначьте тому же стажёру: существующее назначение возвращается без ошибки
   и без дубля. Новое отдельное ТЗ можно назначить тому же человеку.
5. Под стажёром откройте «ТЗ от наставника» и назначенное ТЗ. Должны быть видны
   закреплённая версия, автор, требования, результат и критерии.
6. Наставник готовит версию 2, меняет текст, сохраняет и публикует.
   Стажёр всё ещё видит v1; сначала «Посмотреть версию 2», затем явный переход.
   Права, технические проверки и verified от этого не меняются.
7. Архивирование ТЗ запрещает новые назначения; это архив ТЗ, а не обращений.

## 3. Связь с наставником

1. В конкретном разделе ТЗ нажмите «Спросить наставника»: экран переходит к открытой
   форме связи, выбранный раздел включён в контекст. Повторный клик также работает.
2. Введите вопрос → «Показать текст сообщения». Проверьте ТЗ/версию/раздел или goal/step,
   безопасные факты и вопрос. Полного чата, сырых логов, паролей и закрытых ссылок нет.
3. «Только скопировать» копирует перепроверенный текст. Запретите clipboard браузеру:
   должна быть понятная ошибка, без заявления о доставке.
4. Telegram открывается только по явному действию, URL — https://t.me/username без текста
   вопроса в query. Автоматических отправки, ответа и статуса «доставлено» нет.
5. Клик/copy не закрывает blocker и не ставит verified. В меню нет архива обращений.
6. Через 10 минут старый preview должен потребовать обновления; после изменения состояния
   шага или версии/контакта сервер также отклоняет устаревший экспорт.

## 4. Понятность ТЗ и статистика наставника

1. Создайте отдельное ТЗ «Проверка понятности», назначьте intern-d…intern-i.
2. Intern-d: один раздел → «Непонятно» → «Неясен результат» → «Отметить».
   Повторите трижды: всё ещё один участник, отчёта пока нет.
3. Intern-e: тот же раздел/версия/причина. Наставник → «Понятность заданий»:
   ровно один отчёт, 2 участника, наблюдение/гипотеза/предложение, без списка людей.
4. Intern-f: та же группа → count=3. Intern-g и intern-h: другой раздел и одна другая
   причина → отдельная группа count=2. Intern-i: третий раздел в одиночку → статистика
   скрывает точные числа малой группы, отчёт не создаётся.
5. Наставник → «Статистика» → «Понятность моих ТЗ». Проверьте группы 3 и 2,
   скрытую малую группу, дневную динамику и фильтры 7/30/90 дней, ТЗ/раздел/причина.
   График имеет данные за сегодняшний день; прошлые дни не выдумываются. Разные версии
   не смешиваются; при отсутствии exposure нет процента от всего штата.
6. Откройте отчёт: «Взять в работу» → «Принять гипотезу». ТЗ не должно меняться само.
   Вручную опубликуйте исправленную версию, затем закройте отчёт этой версией.
7. Нажатие «Обновить»/просмотр статистики не создаёт новые отметки и отчёты.

## 5. Технические трудности и обратная связь документации

1. Под двумя новыми стажёрами пройдите доступ и вызовите SSL disable, как в разделе 1.
   У одного повторите проверку: попыток больше, уникальных стажёров всё ещё два.
2. Наставник → статистика технических трудностей: DB_SSL_REQUIRED, уникальные участники,
   наблюдения и открытые блокеры. Это отдельный источник от неясности ТЗ.
3. Владелец документации → «Пробелы знаний»: после двух разных стажёров один candidate
   для journey/step/error. В его статистике только назначенные ему инструкции/версии.
4. Рассмотрите и примите гипотезу: текст инструкции автоматически не публикуется.
   «Resolved» требует проверенной ссылки на исправленную версию.
5. CHECK_UNAVAILABLE/сбой LLM не должен становиться обвинением наставника или дефектом ТЗ.

## 6. Чат, интерфейс и ограничения доступа

- Подсказка в чате отправляет вопрос одним кликом; повторный POST блокируется до ответа.
  Ответ и источники сохраняются после refresh. Источники открываются с повторной ACL.
- «Демо · без LLM» — штатный offline. Нет server metadata — источник не подтверждён.
  Слова модели «я ИИ» не доказывают primary. Реальная LLM в этом стенде не проверяется.
- Проверьте остановку генерации, пустой вопрос, потерю сети и восстановление страницы.
- Intern-c/buddy-b не видят чужие цели, ТЗ, отчёты или статистику команды A.
  Прямая ссылка на чужой объект также запрещена. Согласующий/docs-owner не получают
  редактор ТЗ из-за общей команды.
- На ширине 390px нет горизонтального скролла; меню закрывается, поля и кнопки доступны
  с клавиатуры. Смена аккаунта не показывает данные предыдущего стажёра.

## 7. Сохранность и автоматические проверки

Перезапустите без удаления данных:

```sh
DEMO_FRONTEND_PORT=15174 DEMO_BACKEND_PORT=18081 python3 -m scripts.demo restart --project ai-buddy-demo-v3
make check
npm run build --prefix frontend
npm run test:coverage --prefix frontend
```

После restart проверьте сохранность progress, назначенной версии, решений review и истории
чата. Backend/mock tests требуют отдельной `buddy_test_*` БД; не направляйте их на demo DB.
Browser E2E полного DB пути запускайте только на новом отдельном QA dataset (сценарий меняет
прогресс). Go race, cold CI и платная live LLM имеют отдельные gates, не PASS на fallback.

При дефекте запишите роль/account, URL, шаги, ожидание/факт, время и request_id из ошибки.
Не прикладывайте ключи, cookie, raw logs или реальные персональные данные.
