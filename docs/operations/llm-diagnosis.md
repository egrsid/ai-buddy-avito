# V3-LLM-DIAG-01 — почему в чате отвечал fallback, а не LLM

13 ноября 2026, AI Engineer. Стенд: Docker Desktop (Windows), Cloud.ru OpenAI-compatible `/v1`,
цепочка `GigaChat/GigaChat-3-Pro` → `ai-sage/GigaChat3.5-432B-A28B` → offline.
Все вопросы задавались через публичный Go API (`/api/v2/conversations/{id}/runs` + SSE),
как из браузера. Ключ, тексты чатов и provider payload в отчёт и логи не попадали.

## Итог

Провайдер был здоров. Fallback давали три независимые причины, две из них в AI-сервисе:

| # | Причина | Кто видел | Класс (design §) | Исправление |
|---|---|---|---|---|
| 1 | `make main-demo` / `demo-up` всегда запускают mock: `scripts/demo.py` задаёт `LLM_MODE=mock`, `LLM_API_KEY=""`, `compose.demo.yaml` — mock для ai-service/backend | Любое демо из main | `config_mock` | `make live-demo` (`scripts/live_demo.py` + `compose.live.yaml`): тот же стенд, live из `.env`, проверка до Docker |
| 2 | GigaChat-3-Pro отвечает **400** «Unexpected assistant / user message», если диалог не чередуется строго user→assistant с user в начале. Go шлёт последние 20 сообщений: после 10 вопросов окно начинается с ответа; после упавшего run два вопроса стоят подряд | Любой чат длиннее 10 вопросов | `schema_invalid` (наш запрос) | `prompt.alternate_dialog`: ответы до первого вопроса отбрасываются, подряд идущие сообщения одной роли склеиваются |
| 3 | Модель **копирует служебную пометку** «Произошла ошибка обращения к LLM… резервная модель» из прошлых ответов в истории. После одного fallback весь чат выглядел упавшим, хотя отвечала основная модель (в логах 0 сбоев) | Чат, где fallback был хоть раз | ложный origin по тексту | `notices.strip_service_notes`: пометки вырезаются из истории до отправки модели |

Причина 2 вдобавок включала circuit breaker на 30 с, и основная модель пропускалась
**для всех** пользователей, а не только в длинном чате.
Причина 3 подтверждает требование design: origin нельзя определять по тексту ответа
(V3-LLM-OBS-01, ResponseOrigin от сервера).

| Сообщения после system | GigaChat-3-Pro | GigaChat3.5 |
|---|---|---|
| user | 200 | 200 |
| assistant, user | **400** Unexpected assistant | 200 |
| user, user | **400** Unexpected user message | 200 |
| system, system, user, assistant, user | 200 | 200 |

## Замеры: 10 вопросов подряд, один чат intern-a, публичный Go API

| Прогон | primary | secondary по тексту | Реальных сбоев провайдера | Первый текст | Весь ответ |
|---|---|---|---|---|---|
| До исправлений | 5 | 5 (400 на 6-м вопросе и дальше) | 2 × 400 | 0.8–2.2 с | 3.9–13.1 с |
| Только фикс #2 | 3 | 7 | 0 (все 10 вызовов — Pro, 200) | 0.8–1.4 с | 4.2–8.0 с |
| Фиксы #2 + #3 | **10** | 0 | 0 | 0.72–1.7 с | 3.2–5.8 с |
| `make live-demo`, чистый стенд | **2/2** | 0 | 0 | 0.70–0.75 с | 4.2–4.9 с |

Все run завершились `run.completed`. Go ограничивает 5 run в минуту на стажёра (429
`RATE_LIMITED`), поэтому вопросы шли с интервалом 13 с. Это ограничение Go, а не провайдера.
Расход журнала за диагностику около 19 ₽ (с 5.27 до 24.23 ₽ при стопе 800 ₽), один вопрос
стоит примерно 0.32–0.48 ₽: вход растёт с историей, 2.6–4.3 тыс. токенов.

## Проверено и не является причиной

- Конфигурация контейнера в live: mode/provider/models/base URL верные, ключ задан, `/readyz` ok.
- Сеть контейнеров: Windows-прокси Hiddify обходится через `ProxyOverride=*.cloud.ru;cloud.ru`.
  Если fallback вернётся после переподключения VPN, сначала проверить это.
- `QUERY_EMBEDDINGS=off` отключает только векторный поиск по вопросу и на генерацию не влияет.
- Таймеры (6 с до первого куска, 20/25/85/90 с) не менялись, бюджетный guard тоже.

## Остаётся (не сделано в этом проходе)

- V3-LLM-OBS-01: серверный `ResponseOrigin` (mode/origin/completion/reason_code) вместо
  распознавания фраз на фронтенде. Нужен contract gate BE↔AI↔FE.
- Ошибка 400 сейчас тоже включает breaker на 30 с. Предложение: на 4xx запроса (кроме
  408/429) не выключать модель для всех. После фикса #2 такие 400 не наблюдались.
- V3-T21…T24: отдельный fault-прогон (secondary/offline/cooldown/бюджет/отмена) на live.
