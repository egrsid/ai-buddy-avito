**TL:** после поставки адаптирует runners и выполняет target startup/role isolation/restart.

### AI-R2 · P0: ответ не проверяется по response schema

Валидный JourneySelectionRequest: intent="???", пять allowed_journeys с разными
journey_id, version=1, title из 200 кириллических символов, валидный access_scope.
POST /internal/v2/journey-selection с service token/UUID возвращает **200**, clarification
длиной **1051**, тогда как JourneySelectionResponse разрешает максимум **1000**.
Проверено: input schema=true, output schema=false. api.structured валидирует только вход.

**AI, RP-AI-CORE-01:** ограничить формируемый результат и валидировать все structured
responses перед 200; добавить boundary tests для максимальных разрешенных входов и
некорректного результата handler. Без новых односторонних wire error codes: если нужен
новый error variant, согласовать конкретный schema diff с BE/TL. **Backend:** повторная
валидация upstream остается обязательной; invalid output не создает Action.

### AI-R3 · P0: deadline не перепроверяется перед успешным terminal event

Детерминированная проверка run_generate с injected clock: t=0; provider отдает "ok",
затем при EOF переводит clock на 86; pipeline_timeout=85, first_token=20, idle=25.
Фактическая последовательность: run.started → message.delta → message.sources →
**generation.completed**, без LLM_TIMEOUT. После pending.result/EOF нет проверки deadline.
В api.structured также отсутствует контроллер 85s, есть только имитация timeout fault.

**AI, RP-AI-CORE-01:** считать pipeline от принятия запроса, проверить время после
retrieval/provider result/EOF и перед sources/tool/completed; добавить deadline boundary
tests без долгих sleep и проверку budget для непотоковых операций. Ошибка после начала
потока дает ровно один run.failed, без поздних sources/tool/completed; provider очищается.
**Backend, RP-CHAT-01:** собственный 90s deadline и atomic terminal transition обязательны,
late completion/EOF/cancel не сохраняют action и не перезаписывают terminal state.

### AI-R4 · приемочный runner: общий успех при functional failure

В копии результата evals.run_cases() добавлен failure только в non-safety кейс

для exit 0. Это не провал текущего набора (он весь зеленый), а пробел приемочного gate.

**AI, RP-AI-DIAG-01:** общий итог/exit должен падать при любом провале обязательного P0
