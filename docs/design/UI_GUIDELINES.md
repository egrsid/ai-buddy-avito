# AI-buddy — UI Design Guidelines

**Версия:** 1.1  
**Статус:** Visual Design Reference  
**Основной референс:** `docs/design/ui-reference.png`  
**Область применения:** интерфейсы стажёра и buddy (MVP).

## 1. Общая концепция

AI-buddy — современное веб-приложение для адаптации стажёров Авито.

Интерфейс должен выглядеть дружелюбным, минималистичным, технологичным и профессиональным.

**Основные принципы:**
- AI-чат — центральный элемент пользовательского опыта.
- Прогресс адаптации и связанные задачи всегда легко доступны.
- Пользователь должен понимать текущее состояние любого процесса.
- Сложные действия выполняются пошагово с подтверждением.
- Единый визуальный стиль для стажёра и наставника.
- Минимум лишних экранов, кликов и визуального шума.

Референс определяет визуальное направление, но не является точной спецификацией поведения компонентов.

## 2. Цветовая палитра

На основе предоставленного изображения предлагаем следующие дизайн-токены. Значения приблизительные и должны быть централизованы в теме приложения.

| Токен | Цвет | Применение |
|---|---|---|
| `primary` | `#7839ED` | Основные кнопки, активные элементы |
| `primary-hover` | `#6427D6` | Hover |
| `primary-light` | `#F0EAFF` | Выделение и сообщения пользователя |
| `background` | `#FAF9FE` | Фон приложения |
| `surface` | `#FFFFFF` | Карточки, чат, панели |
| `surface-muted` | `#F6F5FB` | Второстепенные блоки |
| `text-primary` | `#171722` | Основной текст |
| `text-secondary` | `#77768A` | Подписи, метаданные |
| `border` | `#E7E5F0` | Контуры элементов |
| `success` | `#2DBE57` | Завершённые задачи |
| `warning` | `#F2C46D` | Ожидание согласования |
| `error` | `#E45757` | Ошибки |

Цвет не должен быть единственным индикатором статуса: использовать текст и иконки.

## 3. Типографика

Рекомендуемый шрифт: **Inter**, с поддержкой кириллицы.

- Заголовок страницы: 24–28 px, semibold.
- Заголовки карточек: 18–20 px, semibold.
- Основной текст: 14–16 px.
- Кнопки и элементы управления: 14 px, medium.
- Подписи и временные отметки: 12–13 px.

Использовать чёткую иерархию, нормальную высоту строки и минимум декоративных шрифтов.

## 4. Layout

Основной desktop-layout состоит из трёх областей:

### Левая панель — Navigation

Ширина: примерно 250–270 px.

Содержит:
- Логотип Avito AI-buddy.
- Переключатель роли (для тестовых пользователей).
- Основную навигацию.
- Карточку помощника в нижней части.

Навигация стажёра:
- Чат с AI-buddy
- Мой онбординг
- Мои заявки
- Источники открываются из чата в drawer; отдельный каталог базы знаний вне MVP.

Активный раздел выделяется светло-фиолетовым фоном и фиолетовой иконкой.

### Центральная область — Workspace

Основная рабочая область шириной примерно 680–850 px.

Для страницы AI-чата:
- Шапка с аватаром AI-buddy.
- История сообщений.
- Контекстные карточки действий.
- Быстрые подсказки.
- Поле ввода внизу.

Чат должен занимать максимальное доступное пространство и иметь независимую прокрутку.

### Правая панель — Context Sidebar

Ширина: примерно 350–420 px.

Содержит:
- Прогресс онбординга.
- Ближайшие задачи.
- Активные заявки.
- Полезные ресурсы.
- Быстрый переход к наставнику.

Информация должна обновляться после действий пользователя без перезагрузки страницы.

## 5. Компоненты

### Карточки

- Белый или очень светлый фон.
- Скругления 16–20 px.
- Тонкая граница.
- Мягкие тени.
- Внутренние отступы 16–24 px.
- Расстояние между карточками 12–20 px.

### Кнопки

**Primary:** фиолетовый фон, белый текст. Используется для основного действия.

**Secondary:** белый фон, тонкая граница, нейтральный текст.

**Ghost:** минимальная стилизация для дополнительных действий.

Для опасных или изменяющих состояние операций требуется явное подтверждение.

### Поля ввода

- Скругления 10–14 px.
- Светлая граница.
- Отчётливое focus-состояние.
- Отдельные состояния ошибок и disabled.
- Подписи не заменять одними placeholder.

### Иконки

Рекомендуется использовать Lucide Icons.

- Единая толщина линий.
- Размер 18–24 px.
- Последовательное применение цветов.
- Иконки дополняют текст, но не заменяют его.

## 6. AI Chat

Чат — основной компонент продукта.

### Сообщения пользователя

- Располагаются справа.
- Светло-фиолетовый фон.
- Скруглённые углы.
- Небольшая временная отметка.

### Сообщения AI-buddy

- Располагаются слева.
- Светлый нейтральный фон.
- Аватар AI-buddy.
- Поддержка Markdown, ссылок, списков и структурированных блоков.

### Интерактивные действия

AI может показывать специальные компоненты внутри диалога:

- Форму запроса доступа.
- Карточку подтверждения.
- Статус заявки.
- Ссылку на задачу онбординга.
- Карточку передачи вопроса наставнику.
- Источники информации.

Формы должны быть настоящими интерактивными компонентами, а не текстовой имитацией.

### Состояния

Обязательно реализовать:
- Ожидание ответа LLM.
- Выполнение инструментов.
- Успешное завершение действия.
- Ошибку или таймаут.
- Возможность повторить безопасную операцию.
- Отсутствие достоверного ответа.

Не показывать успешное выполнение до подтверждения результата backend.

## 7. Интерфейс онбординга

План адаптации отображается в виде интерактивного списка задач.

Каждая задача имеет:
- Название и описание.
- Статус.
- Связанные материалы.
- Возможность открыть детали.
- Возможность обсуждения с AI-buddy.

**Статусы:**
- `todo` — не начата.
- `in_progress` — выполняется.
- `blocked` — есть препятствие.
- `done` — завершена.

Прогресс должен вычисляться из фактических статусов задач.

Клик по задаче открывает её детали и предоставляет AI контекст выбранной задачи.

## 8. Заявки на доступ

Использовать структурированные карточки и формы.

Основные элементы:
- Название ресурса.
- Уровень доступа.
- Обоснование.
- Кнопка подтверждения.
- ID заявки.
- Текущий статус.

Предусмотреть состояния:
- Черновик.
- Ожидает подтверждения пользователя.
- Отправлена.
- На согласовании.
- Одобрена / отклонена.
- Ошибка отправки.

**Созданная заявка не означает предоставленный доступ.**

## 9. Интерфейс buddy

Использовать ту же дизайн-систему, но адаптировать рабочую область под наставника.

Основные разделы:
- Обращения стажёров.
- Детали обращения.
- Ответ стажёру.
- Статус решения.

Карточка обращения показывает:
- Имя тестового стажёра.
- Связанную задачу.
- Вопрос.
- Согласованную для передачи сводку контекста.
- Статус обращения.
- Единая кнопка «Ответить и закрыть»; атомарный переход в `resolved`.

**Не создавать отдельную дизайн-систему для buddy.**

## 10. Адаптивность

### Desktop (от 1280 px)

Трёхколоночный layout, как на референсе.

### Tablet (768–1279 px)

- Левая навигация компактнее.
- Основная область занимает больше места.
- Правая панель переносится в drawer или отдельный раздел.

### Mobile (до 767 px)

- Одна основная колонка.
- Навигация через выдвижное меню.
- Чат занимает всю доступную ширину.
- Формы адаптируются под маленький экран.
- Важные действия остаются доступными без горизонтальной прокрутки.

## 11. UX и доступность

- Клавиатурная навигация.
- Видимые focus-состояния.
- Контрастный текст.
- Подписи для элементов управления.
- Состояния loading, error и empty.
- Отсутствие блокировки интерфейса при длительных LLM-запросах.
- Понятные сообщения об ошибках.

## 12. Рекомендуемые технологии

Стек утверждён в `ARCHITECTURE.md`; ниже его UI-часть:

- React + TypeScript.
- Tailwind CSS.
- Lucide React.
- TanStack Query для серверного состояния.
- Zustand только при необходимости глобального клиентского состояния.
- Zod для проверки данных на границах интерфейса и API.

Повторно используемые компоненты должны находиться в общей UI-библиотеке приложения.

## 13. Правила для AI-агентов разработки

Перед реализацией frontend-функциональности:

1. Прочитать этот документ.
2. Изучить `docs/design/ui-reference.png`.
3. Прочитать продуктовую спецификацию.
4. Проверить существующие UI-компоненты.
5. Переиспользовать дизайн-токены и общие компоненты.
6. Не создавать собственные несогласованные стили.
7. Реализовать необходимые состояния загрузки, ошибок и пустых данных.
8. Проверить адаптивность и доступность.
9. Добавить тесты для нового поведения.

### Приоритет требований

При противоречиях соблюдать порядок:

1. Продуктовая спецификация и требования безопасности.
2. Функциональные спецификации.
3. Этот документ.
4. Визуальный референс.

**Важно:** изображение — концепт, а не фотография работающего приложения. Примеры номеров заявок, статусов, сроков и сообщений на картинке не являются реальными данными или обязательным поведением системы.

## 14. Границы MVP

В MVP реализуются интерфейсы:
- Стажёра.
- Buddy.

Интерфейс HR **не входит в MVP**. Он разрабатывается последним, после завершения и стабилизации основных сценариев.

Дизайн-система должна допускать добавление интерфейса HR в будущем, но сейчас не нужно создавать HR-экраны или HR-компоненты.

## 15. Функциональные границы UI v1

Маршруты и обязательные экраны заданы в продуктовой спецификации, состояния —
в `docs/architecture/state-machines.md`. Неактивные разделы не добавлять ради сходства с картинкой.
Скрепка/загрузка вложений, сроки выдачи реального доступа и обещания уведомить о нём вне MVP.
Каркас приложения до S2 может показывать только состояние подготовки; это не готовый интерфейс.
