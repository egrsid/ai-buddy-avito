# Проверка сценариев

Нужен стенд из [README](../README.md). Переключатель «Демо-аккаунт» находится слева;
intern-b и аккаунты другой команды доступны через «Дополнительные участники».
При повторной проверке используйте новый `--project` или новое имя ТЗ: seed/restart
сохраняют прогресс. Удалять существующие volumes не требуется.

## A. От вопроса до подтверждённого доступа

1. Выберите intern-a → «Мои цели» → «Начать» у доступа к БД команды A.
2. Раскройте подзадачи, откройте проверку доступа и инструкцию. В чате отправьте
   «Подготовь заявку на доступ к тестовой БД». Проверьте источник ответа и ссылку.
3. Просмотрите preview: ресурс `db-team-a-test`, роль `db_reader`, цель и обоснование.
   До «Подтвердить» в «Моих заявках» новой заявки нет. Подтвердите: статус submitted.
4. Выберите approver-a, заполните основание и одобрите. Одобрение отдельно от отправки;
   Go проверяет IAM заново. Вернитесь к intern-a и обновите страницу.
5. Шаг доступа подтверждён IAM evidence. В проверке подключения выберите SSL `disable`:
   результат `DB_SSL_REQUIRED`, blocker и следующее разрешённое действие.
6. Выберите SSL `require` и повторите. Цель достигает 100% по результатам проверок.
   В «Заданиях и целях»/«Почему такой статус?» видны разные факты заявки, IAM и DB check.
7. Обновите страницу: результат сохранён. AI-ответ сам по себе не засчитывает шаг.

В режиме без ключа видна метка «без ИИ»/fallback; с рабочим ключом Cloud.ru ожидается
метка ответа модели. Имитация IAM/DB в обоих режимах остаётся синтетической.

## B. Вопрос наставнику и повторяющаяся ошибка инструкции

1. Пока есть `DB_SSL_REQUIRED`, нажмите «Подготовить сообщение», введите вопрос и
   откройте preview. В нём только разрешённый контекст ошибки/шага.
2. Скопируйте текст. Открытие Telegram не отправляет сообщение и не подтверждает доставку;
   демонстрационные контакты не являются реальными получателями.
3. Повторите сценарий A с SSL-ошибкой под intern-b. Повтор одного intern-a не считается
   вторым человеком. Используйте одинаковые journey/step/error.
4. Выберите docs-owner-a → «Пробелы знаний». Появился один candidate для двух участников.
   Примите гипотезу с основанием: решение сохраняется, исходная инструкция не публикуется
   и не меняется автоматически. Технические проверки и человеческий review различаются.

## C. От неясного ТЗ до опубликованного уточнения

1. buddy-a → «Мои задания» → «Новое ТЗ». Укажите уникальное название, цель,
   ожидаемый результат, критерий приёмки и раздел «Формат» с текстом
   «Опишите результат в свободной форме». Сохраните draft, опубликуйте v1.
2. Назначьте одно ТЗ intern-a и intern-b. Каждый открывает его раздел «Формат»,
   нажимает «Непонятно», выбирает «Неясен результат» и подтверждает отметку.
3. buddy-a → «Улучшение заданий» → выберите отчёт этого ТЗ/раздела/v1.
   В уточнении автора задайте: «Отчёт должен содержать нумерованный список
   выполненных проверок и их результаты». Нажмите «Предложить уточнение».
4. Проверьте «Было», «Предлагается», обоснование и источник. AI может запросить
   недостающие требования. Состояние generating не блокирует обычный редактор.
5. Выберите подходящую правку → «Применить в черновик». Published v1 пока не меняется.
6. Откройте редактор, проверьте текст и отдельно опубликуйте v2. Назначенная v1
   остаётся закреплённой, пока стажёр явно не примет переход на новую версию.
7. На свежем наборе «Настроить сравнение» возвращает «Недостаточно данных»:
   семидневная история не выдумывается.

Для ТЗ, которому нужен DB-маршрут, buddy-a в панели технических целей назначений
явно разрешает его. Intern в «Заданиях и целях» проверяет preview и подтверждает
связь. Разрешение маршрута не выдаёт grant; несколько ТЗ могут использовать один goal.

## D. Сравнение версий на контрольных данных

```sh
python3 -m scripts.v4_cohorts up
```

Откройте http://localhost:15181 в отдельном приватном окне. Под buddy-a в
«Улучшении заданий» выберите отчёт `Synthetic: сравнение двух версий задания · Формат · v1`
и загрузите сравнение. Ожидание: A 6/10 = 60%, B 2/10 = 20%, −40 п.п.,
явная подпись синтетических тестовых часов. Это отдельная БД и 20 test-участников,
созданных через бизнес-API. Повтор команды не обнуляет сценарий.

## E. Доступ и отказы

- intern-c не читает цель/инструкцию команды A по прямому URL: 403/404 без чужого текста.
- Наставник не получает личную timeline другого человека по общей роли.
- Prompt injection не выдаёт прав, не меняет verified и не раскрывает закрытые источники.
- Expired/изменённый preview требует обновления; повтор confirm не создаёт вторую заявку.
- При недоступности модели видны причина/источник fallback; ручные действия доступны.
- На 390px и с Tab/Enter доступны основные карточки, раскрытия и действия.

## Проверка сдачи DB-задания, перехода из заявки и RP-QA-01

### Подготовка

Из корня рабочей копии запустите отдельный стенд с чистым v2 seed. Нужны
Docker с Compose и Python 3.12. Стенд использует учебные IAM и БД, ключ модели не нужен.
Если этот проект уже запускался, выберите новое имя с префиксом `ai-buddy-demo-`.

```sh
python3 -m scripts.demo up --project ai-buddy-demo-submission-check
```

Откройте http://localhost:15173. Аккаунты переключаются в меню «Демо-аккаунт».

### 1. Создайте ТЗ и свяжите его с технической целью

1. Под `buddy-a` откройте «Мои задания» → «Новое ТЗ». Укажите уникальное название,
   например «QA — проверка подключения к БД». В ожидаемом результате укажите
   «Короткий вывод об успешном подключении», а в критерии приёмки — «Указан режим SSL».
   Заполните цель и раздел ТЗ, сохраните черновик, опубликуйте версию 1 и назначьте её `intern-a`.
2. В «Улучшение заданий» раскройте «Дополнительно: технические цели назначений».
   Найдите это ТЗ и `intern-a`, отметьте «Для этого назначения нужен доступ к БД команды A»
   и нажмите «Добавить цель доступа к БД».
3. Под `intern-a` откройте «Задания и цели». В карточке ТЗ нажмите «Связать с технической целью»,
   затем «Подтвердить связь». Должна появиться связанная цель доступа к БД команды A.
4. Нажмите «Открыть ТЗ» → «Сдача работы». До успешной проверки подключения видна подсказка
   со ссылкой «Задания и цели». Поле вывода и кнопка отправки появятся после проверки.

### 2. Проверьте переход из одобренной заявки

1. Под `intern-a` в «Мои цели» раскройте шаги связанной цели и откройте «Проверить доступ».
   В чате попросите подготовить заявку на доступ к тестовой БД, проверьте ресурс `db-team-a-test`
   и роль `db_reader`, затем нажмите «Подтвердить». Пока заявка отправлена и ждёт решения,
   в «Моих заявках» нет ссылки перехода к проверке.
2. Под `approver-a` откройте «Согласования», заполните основание и нажмите «Одобрить».
   Вернитесь под `intern-a` в «Мои заявки».
3. Если IAM подтвердил доступ, ссылка «Проверить подключение к БД» открывает шаг подключения
   в той же цели. Если заявка одобрена и IAM ещё не подтвердил доступ, ссылка
   «Проверить доступ в IAM» открывает шаг проверки доступа для этой цели. На обычном
   демостенде после одобрения ожидается первый вариант. Обе развилки проверяет
   [тест страницы заявок](../frontend/src/pages/LiveAccessPages.test.tsx).
4. На шаге подключения выберите режим SSL `require` и запустите проверку. Цель должна
   достигнуть 100%. При желании сначала проверьте режим `disable` на свежей цели.
   Он должен привести к `DB_SSL_REQUIRED`, а форма сдачи по-прежнему недоступна.
   После этого повторите проверку с `require`.

### 3. Проверьте сдачу, возврат и приёмку

1. Под `intern-a` откройте «ТЗ от наставника» → это ТЗ → «Сдача работы». Убедитесь,
   что видна дата успешной проверки и кнопка «Передать наставнику» недоступна при пустом
   выводе. Введите «Подключение к тестовой БД подтверждено» и отправьте. Ожидаемый статус
   «У наставника на проверке», попытка 1, версия ТЗ 1.
2. Под `buddy-a` откройте «Мои задания» → это ТЗ → «Назначения» → «Проверка работы» у
   `intern-a`. Сверьте вывод, дату проверки и идентификатор доказательства. Убедитесь,
   что «Вернуть на доработку» недоступна при пустом комментарии. Введите «Укажите режим SSL»
   и верните работу. Ожидаемый статус «Возвращено на доработку».
3. Под `intern-a` снова откройте «Сдача работы». Проверьте комментарий наставника,
   укажите `ssl_mode=require` в выводе и отправьте. Ожидаемый статус
   «У наставника на проверке», попытка 2.
4. Под `buddy-a` откройте «Проверка работы» и нажмите «Принять работу».
   Под `intern-a` снова откройте ТЗ и обновите страницу. После раскрытия «Сдача работы»
   ожидается «Работа принята», попытка 2. Форма отправки скрыта, а в «Мои цели»
   технический прогресс по-прежнему 100%.
5. Для проверки доступа скопируйте адрес ТЗ под `intern-a` и откройте его под `intern-b`.
   ТЗ и вывод `intern-a` должны быть недоступны.

### 4. Запустите автоматические проверки

На компьютере с Node.js 26 из корня репозитория выполните команды ниже. Для проверки
используйте тот же адрес, на котором запущен frontend. При первом запуске потребуется
установка зависимостей и Chromium.

```sh
cd frontend
npm ci
npx playwright install chromium
E2E_BASE_URL=http://localhost:15173 npx playwright test e2e/onboarding.spec.ts e2e/work-submission.spec.ts --workers=1 --reporter=list
```

Ожидается **3 passed**. Два теста RP-QA-01 проверяют владение целью, команды стажёров,
версию маршрута, расчёт прогресса, сессию и CSRF. Браузерный тест проверяет сдачу,
возврат, повторную отправку и приёмку с настоящим Go API. Проверку обеих ссылок
из одобренной заявки можно прогнать отдельно из `frontend/`.

```sh
npm test -- src/pages/LiveAccessPages.test.tsx
```

- [Тесты RP-QA-01](../frontend/e2e/onboarding.spec.ts)
- [Браузерный тест сдачи](../frontend/e2e/work-submission.spec.ts)

Полный автоматический сценарий, включая настоящий restart и ACL,
описан в [запуске тестов](testing.md). Проверки используют synthetic данные.
