# Повторяющиеся затруднения и человеческий review — спецификация

## Цель и предусловия

Есть trusted error инструкции либо structured отметка intern о неясности назначенного раздела ТЗ. Scope источника и reviewer проверен.

## Пользовательский сценарий

Первый сигнал → повтор другого участника → детерминированная группа → безопасная AI-гипотеза либо шаблон → reviewer рассматривает → accepted/rejected либо resolved с проверенной опубликованной версией.

## Правила и критерии приёмки

- **FEEDBACK-01.** Технический friction группируется по journey_id + step_id + normalized error_code. Порог — два distinct interns; повтор одного и повтор доставки порог не повышают.
- **FEEDBACK-02.** Task clarity — отдельная группа TaskBrief/version/section/reason. Технические ошибки и неясность задания не смешиваются.
- **FEEDBACK-03.** Группировка, distinct count, threshold и dedup принадлежат Go. AI не решает, кого считать, и не создаёт события от имени людей.
- **FEEDBACK-04.** Недоступность внешнего сервиса сама по себе не доказывает дефект документации. Гипотеза описывает текст/процесс, не обвиняет и не оценивает сотрудника.
- **FEEDBACK-05.** Reviewer видит только scoped aggregate без raw logs/PII/chat/списка участников. Нельзя раскрыть чужие заголовки или ссылки через aggregate.
- **FEEDBACK-06.** Accepted означает согласие с гипотезой; не публикует документ, не выдаёт grant и не закрывает technical blocker. Resolved требует разрешённой проверенной версии.

## Контрольный пример

Две ошибки SSL одного intern не дают candidate. Та же ошибка второго intern даёт ровно один. Неясность «Формат» этого же ТЗ рассматривается в другом report.
