# Product Spec v3 — помощь в Telegram и понятность заданий

Статус: целевое поведение, реализация TODO. Текущий работающий релиз — v2/main b6f940d.

## Проблема и результат

Стажёру проще написать наставнику в привычном Telegram, чем создавать внутреннее обращение.
При этом повторяющаяся неясность задания должна помогать наставнику улучшать его постановку.
Продукт сохраняет сопровождение до проверенного результата и организационную обратную связь.

Стажёр: цель/ТЗ → разрешённое действие/проверка → затруднение → личный Telegram наставника.
Обучающий цикл: разные стажёры не понимают один раздел одной версии ТЗ → безопасный агрегат →
гипотеза наставнику → ручное редактирование → новая опубликованная версия ТЗ.

## Роли и права

| Роль | V3 |
|---|---|
| Стажёр | Свои назначения/опубликованное ТЗ, отметка конкретного неясного раздела, Telegram-контакт назначенного наставника |
| Наставник | Создать/редактировать/публиковать свои ТЗ; назначить стажёрам своей разрешённой области; смотреть агрегаты своих ТЗ |
| Согласующий доступ | Прежние resource-scoped решения; роль наставника сама по себе этого права не даёт |
| Владелец документации | Прежние scoped Knowledge Gap Candidates и human review |

Новых прикладных ролей нет. Назначенный наставник и автор ТЗ могут различаться:
контакт определяется buddy assignment стажёра, получатель отчёта — owner данного ТЗ.
Переназначение проверяет Go; совпадение team_id без явных полномочий не открывает чужое ТЗ.

## P0 версии 3

1. «Написать наставнику в Telegram» вместо создания escalation. Настраиваемый контакт,
   безопасный preview/копирование контекста, отсутствие ложного статуса доставки.
2. Структурированный редактор ТЗ: цель, описание, стабильные разделы, ожидаемый результат,
   критерии приёмки, разрешённые ссылки. Draft → published → archived; published immutable.
3. Стажёр указывает раздел своего задания и причину: «Неясно требование», «Неясен результат»
   или «Неясен критерий приёмки». Система показывает «затруднение сообщено», не technical evidence.
4. Два разных стажёра одной области/версии/раздела/причины за 30 дней → один Task Clarity Report
   владельцу ТЗ: наблюдение, count, версия/раздел, гипотеза и предложение улучшения.
5. Наставник принимает/отклоняет гипотезу, вручную готовит новую версию ТЗ и публикует её.
   Отчёт resolved только после явной привязки опубликованного исправления.
6. Старый documentation feedback loop сохраняется отдельно. DB_SSL_REQUIRED сам по себе
   не означает плохую формулировку задания и автоматически не создаёт отчёт наставнику.

## Разделение сигналов

| Сигнал | Получатель | Ограничение |
|---|---|---|
| Повторная ошибка шага/инструкции v2 | Владелец документации | Существующие journey/step/error и 2 distinct interns |
| Повторная структурированная неясность раздела ТЗ | Владелец ТЗ/наставник | task/version/section/reason в scoped группе |
| Личное сообщение | Telegram назначенного наставника | Продукт не знает факт отправки/доставки/ответа |

Оба отчёта возможны при независимых основаниях, с отдельными ACL/состояниями. AI не
назначает виновного, не выводит качество наставника из частоты ошибок и не создаёт
связь между потоками без явных разрешённых ссылок. Никаких рейтингов/HR dashboard.

## Инварианты

Новая редакция ТЗ не меняет права, mandatory journey steps, evidence или verified.
Существующие назначения закреплены за опубликованной версией; переход на новую — отдельный
preview/confirm с expected_version, без тихой замены текста. При отсутствии автоматической
проверки результат ТЗ остаётся «не проверен»; человеческий отзыв не притворяется DB evidence.
Сообщение в Telegram не выставляет waiting_external/verified и не закрывает blocker.

## Демонстрация v3 после реализации

Наставник создаёт и публикует ТЗ с неоднозначным разделом, назначает двум стажёрам.
Первый отмечает неясность, открывает Telegram либо копирует контекст; отчёта пока нет.
Его повторная отметка не увеличивает count. Второй отмечает тот же раздел/причину —
один отчёт count=2. Наставник видит гипотезу, уточняет критерий, публикует v2 ТЗ и связывает
исправление; старые назначения остаются v1 до явного перехода. Отдельно проходит прежний
DB/approval/check и documentation-owner сценарий; очереди личных обращений больше нет.

## Дополнение владельца: цели, реальная LLM и статистика

Все три пункта — P0 v3, пока PLANNED. Они дополняют Telegram/ТЗ/feedback, не заменяют их.

- [Карточки целей](../features/goal-subtask-disclosure/spec.md): цель и её прогресс — основной
  блок списка; кнопка раскрывает подзадачи, поддерживаются несколько целей, зависимости,
  прямые ссылки, клавиатура. Verified считает Go, сворачивание не меняет прогресс.
- [Live LLM](../features/live-llm-reliability/spec.md): штатный live ответ — primary модель,
  secondary/offline только по настоящей причине. Сначала выяснить фактический launch mode;
  текущий offline runner принудительно mock. Нельзя «починить» это ложной меткой «ИИ» или
  удалением fallback. Нужны реальные provider/run evidence, smoke и отдельные fault tests.
- [Статистика](../features/intern-difficulty-statistics/spec.md): наставнику — технические
  трудности назначенной ему группы и отдельно понятность собственных ТЗ; владельцу документов —
  трудности его инструкций/версий. Период, unique affected, наблюдения, причины, динамика,
  открытые blockers/reports; counts формирует Go с ACL до aggregation. Никаких рейтингов людей.

### Дополнение к demo v3

Показать две цели свёрнутыми: прогресс виден сразу. Раскрыть одну, перейти к подзадаче,
запустить допустимую проверку; сворачивание и обновление сохраняют корректный процент.
На отдельно подготовленном live-стенде задать вопрос и показать подтверждённый primary
ответ. Fault сценарий показывать отдельно, с честной меткой и причиной перехода к резерву.
Затем по фиксированным synthetic событиям открыть статистику наставника и документации:
разные разрешённые разрезы/счётчики, drill-down в report, отредактировать ТЗ/инструкцию
в прежнем human review flow. Статистика сама не публикует исправления.
