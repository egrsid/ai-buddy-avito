## 1. Проблема, видение и ценность

Стажёр может получить объяснение или сгенерированный ответ, но не понимать, что делать
дальше и как проверить успех. Неполная инструкция создаёт одинаковые блокеры у разных
людей; наставник восстанавливает диагностику с нуля, а организация не получает обратной связи.

[Видение](vision.md): сопровождать инженерную цель до проверенного результата и
превращать повторяющиеся затруднения в проверяемые человеком предложения улучшений.
Для стажёра это следующий допустимый шаг и evidence, для buddy — контекст диагностики,
для организации — обезличенная карточка повторений. RAG и объяснение терминов —
вспомогательные возможности, не центр продукта и не доказательство уникальности.

## 2. Роли и области доступа

| Роль | P0-операции | Ограничение |
|---|---|---|
| intern | Своя цель, проверки, черновик, подтверждение отправки, эскалация | Команда + ресурс + разрешение; только свои данные |
| buddy | Очередь назначенных стажёров, диагностическая карточка, ответ | Только явно переданный разрешённый snapshot; без всей истории |
| access_approver | Одобрить/отклонить mock-заявку | Только назначенные ресурсы; не сам стажёр |
| documentation_owner | Рассмотреть Knowledge Gap Candidate | Только назначенные инструкции и агрегаты; без персональных данных |

Это четыре прикладные роли, а не четыре разных приложения. Пять участников разработки
не являются этими тестовыми пользователями. Ответственный за документацию не является HR.
Совмещение buddy и approver не даёт прав автоматически: нужны отдельные назначения;
в базовом демо роли разделены. Матрица: [security](../architecture/security.md).

## 3. Модель и бизнес-правила

Goal — экземпляр цели стажёра по фиксированной версии Journey Template. Step имеет
Dependencies, инструкцию, допустимые Actions и Verification Method. Evidence —
доверенное подтверждение; Blocker — причина остановки; Friction Event — безопасная
запись затруднения; Escalation — передача buddy; Knowledge Gap Candidate — гипотеза
улучшения инструкции или процесса.

Состояния шага: `unverified`, `ready`, `blocked`, `waiting_external`, `verified`.
Их вычисляет Go. LLM, кнопка «Готово», ответ buddy и одобрение заявки сами по себе
не переводят результат подключения в `verified`. Утверждение пользователя хранится
отдельно; ручное подтверждение показывается отдельно и не считается техническим evidence.
В P0 проверка автоматическая через mock API. Прогресс = число verified обязательных
шагов / число обязательных шагов, округление вниз; при пустом наборе 0.
Goal verified только при актуальных проверках всех обязательных условий.
Правила свежести и отзыва evidence: [state machines](../architecture/state-machines.md).

Маршрут хранится как заранее утверждённый JSON, не генерируется LLM с нуля.
AI выбирает только из разрешённых маршрутов, объясняет инструкции, заполняет допустимые
поля и предлагает действия. Go валидирует шаблон, граф, доступ и результат.
[Схема маршрута](../architecture/journey-template.md), [данные](../architecture/data-model.md).

## 4. Обязательный сквозной сценарий P0

1. intern-a команды A выбирает цель «Получить доступ к тестовой БД и проверить подключение».
2. Go выбирает разрешённую версию маршрута и проверяет текущий доступ через mock IAM.
3. Доступа нет: Go фиксирует блокер; AI объясняет его и заполняет структурированный
   черновик заявки (ресурс, запрашиваемая роль, основание, обязательные поля).
   Пользователь выводится из сессии, а не из текста LLM.
4. Go валидирует запрос. React показывает точный preview; intern подтверждает отправку.
   Без этого подтверждения external write отсутствует.
5. Go идемпотентно создаёт mock-заявку. Отдельный access_approver принимает решение.
   Таймер и подтверждение стажёра не выдают доступ.
6. Mock IAM фиксирует grant после одобрения; Go повторно читает фактическое разрешение.
   Approved без grant означает ожидание, а не успех.
7. Стажёр запускает безопасную фиксированную проверку подключения без произвольного SQL.
   В проблемном варианте инструкции не описан SSL: mock возвращает `DB_SSL_REQUIRED`.
8. Go сохраняет проверку, blocker и friction event. AI предлагает разрешённое действие
   и preview диагностики buddy: цель, шаг, ошибки, evidence, попытки, инструкции и гипотеза.
9. Intern подтверждает snapshot, назначенный buddy отвечает. Ответ связывается с blocker;
   после безопасной настройки `ssl_mode=require` стажёр повторяет проверку. Только успешный
   доверенный результат переводит шаг и цель в verified.
10. intern-b из той же команды A проходит тот же маршрут и получает ту же ошибку.
    Go группирует `journey_id + step_id + error_code`, считает двух разных стажёров,
    исключает дубли и создаёт один Knowledge Gap Candidate.
11. documentation_owner видит шаг, инструкцию, код ошибки, число людей и гипотезу исправления.
    Он рассматривает предложение. Даже accepted не публикует изменения автоматически.

intern-c команды B, другая БД, ограниченный ресурс и закрытые документы обязательны
для отрицательных тестов. Повторы одного стажёра не достигают порога feedback loop.
Быстрый успешный вариант проходит те же проверки без SSL-ошибки. Подробности: [demo](demo.md).

## 5. Scope и приоритеты

| Приоритет | Состав |
|---|---|
| P0 | Тестовая auth; role/team/resource/document ACL; синтетические сотрудники/ресурсы/закрытые документы; один JSON-маршрут; контекстный AI; mock IAM check; AI draft; confirm отправки; отдельное mock approval; grant check; безопасный DB check; evidence; ошибки и blockers; минимальный buddy handoff; два уникальных стажёра и один candidate; review ответственным; offline demo |
| P1 | Второй маршрут; подробный граф; оптимальный следующий шаг; расширенный buddy UI; история review; более развитый RAG с цитированием; более удобные evidence-карточки; дополнительные проверки |
| P2 | Реальные интеграции; произвольные репозитории/MR/code style; IDE/локальный агент; семантические кластеры; Friction Radar; предложения новых маршрутов; полная аналитика; workflow builder; HR после MVP |

P0 уже требует проверки доступа к источникам и безопасных ссылок, минимального просмотра
и решения по candidate; P1 расширяет эти возможности. При нехватке времени сокращать
второй маршрут, визуализацию, аналитику, семантическую группировку и сложные AI-сценарии.
Не сокращать RBAC, подтверждение, основной маршрут, проверку результата, ошибки,
минимальный feedback loop и offline-воспроизводимость.

Вне MVP: HR dashboard, автономная выдача прав, автоматическая публикация документации,
произвольные SQL/команды, browser extension, IDE plugin, сложная multi-agent платформа,
реальные закрытые системы Авито, полноценный мессенджер, загрузка вложений и голос.

## 6. Интерфейс

Главная `/onboarding`: цель → состояния шагов → blocker → следующее действие → AI.
`/onboarding/{goalId}/steps/{stepId}`: зависимости, инструкция, статус, evidence,
безопасная ошибка и контекстный чат. `/requests`: свои заявки и фактические статусы.
`/buddy/escalations` и `/{id}`: разрешённая диагностика и «Ответить и закрыть».
`/approvals`: минимальное mock-одобрение назначенных ресурсов.
`/knowledge-gaps` и `/{id}`: очередь ответственного, агрегат и решение.
Общий `/chat` вспомогателен; отдельный каталог знаний не обязателен, источники — в drawer.
Визуальный стиль и адаптивность: [UI guidelines](../design/UI_GUIDELINES.md).

## 7. Безопасность и нефункциональные требования

Go аутентифицирует пользователя и вычисляет scope. Python фильтрует документы до LLM,
повторно проверяет фрагменты; Go проверяет ссылки и текущие права при открытии источника.
Защищены также названия, метаданные и цитаты. Только синтетические данные; персональные
данные, секреты, сырые логи и вся переписка не попадают в агрегат/buddy/LLM автоматически.
Python не изменяет app и не вызывает изменяющие корпоративные операции. Любое выполнение
проходит Go; idempotency, повторная авторизация и точное подтверждение обязательны.

Стек React/TypeScript/Tailwind/TanStack Query/Zod + Go + Python/FastAPI + PostgreSQL/pgvector
сохраняется. SSE Python → Go → React; статусы читаются через Go. Docker Compose и
offline/mock provider обеспечивают воспроизводимый путь без реальных API и платного ключа.
Локальные операции ориентированы на отклик <1s; долгие операции показывают ожидание,
таймаут/ошибку и не блокируют интерфейс. Прикладное line coverage строго >80% отдельно
для Go/AI/mock/frontend; метрика и исключения в [testing](../testing/strategy.md).

## 8. Definition of Done

- [ ] Полный путь §4 выполнен через реальные компоненты и синтетические mock API, без SQL-правок разработчика.
- [ ] Успех, отказ, approved без grant и SSL-ошибка различимы; evidence/прогресс сохраняются после refresh/restart.
- [ ] Два уникальных стажёра создают один candidate; повтор одного и повторы доставки его не создают.
- [ ] Buddy получает проверенный snapshot; ответ не подменяет DB check; responsible review не публикует документ.
- [ ] Все отрицательные ACL/privacy/injection/idempotency тесты проходят, закрытые данные не передаются LLM.
- [ ] Offline-путь, SSE, чистая БД, повторные migrate/seed, CI и coverage >80% воспроизводимы.
- [ ] README, восемь SDD, демосценарий, синтетические данные, PDF-презентация и видео соответствуют реализации.
- [ ] Mock/live результаты явно помечены; healthchecks/fixtures не представлены как реализованный MVP.

- [ ] При ошибке LLM согласованная цепочка Pro → 3.5 → offline сообщает в чате об ошибке/fallback и предлагает напрямую обратиться к наставнику; partial не выдаётся за успешный ответ модели.
