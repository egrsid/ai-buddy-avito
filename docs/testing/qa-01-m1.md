# QA-01 · M1 план проверки S2

Статус: подготовлен; сквозной запуск заблокирован до реализации BE-01/02 и FE-02.
Основание: API v1, security.md, onboarding S2 и backlog M1.

## Проверяемый путь

1. Открыть приложение и войти как `intern-a` через demo-login. Проверить профиль
   через `/api/v1/auth/me` и cookie-сессию; роль должна приходить от сервера.
2. Открыть план адаптации. Проверить `GET /api/v1/tasks`: список и прогресс относятся
   только к текущему стажёру. Открыть задачу из ответа, сверить детали и статус.
3. Изменить статус задачи на `in_progress` через интерфейс. Мутация должна передавать
   актуальный `version`, CSRF и `Idempotency-Key`; ответ увеличивает version.
4. Обновить страницу и перезапустить приложение/API без сброса БД. Статус/version
   должны остаться сохранёнными.
5. Отправить устаревший version для своей задачи: ожидать `409 VERSION_CONFLICT`,
   состояние в хранилище не должно перезаписаться.
6. Войти как `intern-b`: список не содержит задачу `intern-a`, прямой запрос к её ID
   даёт `404 NOT_FOUND`. Войти как `buddy-a`: список задач недоступен (`403 FORBIDDEN`).
7. Проверить пустой список: прогресс `done=0`, `total=0`, `percent=0`.

## Предусловия и данные

- Запустить чистое окружение по `make up`, затем `make migrate`, `make seed`.
- Использовать только синтетические seed-аккаунты `intern-a`, `intern-b`, `buddy-a`.
- Не перехватывать бизнес API в E2E: сценарий должен идти через Go, PostgreSQL и UI.
- Для повторяемости брать task ID из списка `intern-a`, не фиксировать UUID в тесте.
- Для PATCH брать `csrf_token` из `/auth/demo-login` или `/auth/me`; задавать ожидаемый
  Origin согласно APP_ORIGIN. На каждую бизнес-мутацию посылать UUID Idempotency-Key.

## Что пока не исполняется

В текущем checkout публичные сценарии ещё не реализованы: frontend показывает только
bootstrap экран; продуктовые auth/tasks handlers и тесты Playwright отсутствуют.
Поэтому данный план фиксирует критерии QA-01 и не выдаёт проверку каркаса за M1.
Добавлен Playwright API integration сценарий в `frontend/e2e/onboarding.spec.ts`:
он проверяет контрактный M1 путь через public API, включая stale version, RBAC,
401 для запросов без сессии и 403/CSRF_INVALID без CSRF-токена с проверкой, что задача
не изменилась.
Он ещё не покрывает браузерные UI-действия и запуск backend после рестарта; это нужно
добавить после готовности BE-01/02 и FE-02, затем запускать полный сценарий на Compose.
