# Проверка и демонстрация AI-buddy v4 для защиты

Основной адрес итогового стенда: **http://localhost:15178**.
Это synthetic local demo, корпоративные сервисы — отдельный mock. Источник данных
«Live API» означает настоящий Go/PostgreSQL, а не обязательно платную LLM. Штатный
режим этого запуска — offline по решению владельца. Прототип /v4-preview — отдельно;
его числа не являются результатом работающей бизнес-системы.

## Запуск и подготовка

Из корня ветки feature/ai-v4 (полная интеграция поверх feature/tl-v4), Docker Desktop запущен.
На любой машине с сетью (первая сборка скачивает зависимости):

```sh
DEMO_FRONTEND_PORT=15178 DEMO_BACKEND_PORT=18085 python3 -m scripts.demo up --project ai-buddy-demo-v4-final
```

Если зависимости уже собраны на этой машине, можно без сети добавить `--offline`:

```sh
DEMO_FRONTEND_PORT=15178 DEMO_BACKEND_PORT=18085 python3 -m scripts.demo up --offline --project ai-buddy-demo-v4-final
```

На стенде есть synthetic ТЗ «V4 review …» после browser test; intern-a имеет связанную,
ещё не завершённую техническую цель. Для репетиции создайте ТЗ с новым названием.

Cached images подготовлены на этом ноутбуке. На новой машине без cache — обычный
`up` без `--offline` при доступной сети. Команда сохраняет БД; reset/down --volumes
не используйте. Предыдущие v3 и QA данные не очищались. Полный автоматический demo-loop
меняет progress и требует отдельной свежей QA БД, не запускайте его на стенде показа.

Роли слева: стажёр intern-a, наставник buddy-a, согласующий approver-a, владелец
документации docs-owner-a. Дополнительные участники: intern-b, intern-d…intern-i команды A;
intern-c/buddy-b другой команды. Вход под тем же аккаунтом в другой вкладке может закрыть
предыдущую сессию. Для новой репетиции возьмите непроходившего путь дополнительного стажёра.

## Что показать за 7–10 минут

### 1. Наставник задаёт понятный результат

1. Наставник → «Мои задания» → «Новое ТЗ». Создайте «Отчёт о подключении»:
   цель — подготовить отчёт; раздел «Формат» — «Опишите результаты в свободной форме»;
   ожидаемый результат — документ с результатами проверок; критерий — перечислены проверки.
2. Сохраните черновик. Стажёр его не видит. Опубликуйте версию 1.
3. Назначьте intern-a и intern-b. Повтор тому же человеку не создаёт дубля.
4. Наставник → **«Улучшение заданий»**. В списке назначений у intern-a нажмите
   «Разрешить DB-маршрут». Разрешение маршрута не выдаёт доступ к самой БД.

### 2. Рабочее пространство и доказательства

1. Intern-a → **«Рабочие результаты»**. Найдите назначенное ТЗ.
2. «Связать с технической целью» → проверьте preview → «Подтвердить связь».
   Без разрешённого наставником template связь отклоняется. Пройденный journey повторно
   не создаётся. «Открыть ТЗ» показывает требования; «Подзадачи и доказательства» — маршрут.
3. Откройте «Проверить доступ». Подготовьте заявку через чат или кнопку, проверьте preview
   и подтвердите отправку. Убедитесь, что до подтверждения заявки нет.
4. Согласующий → одобрить с основанием. **Теперь Go сам запускает свежую IAM-проверку.**
   Шаг засчитывается по IAM evidence, не по нажатию «Одобрить». Если IAM не подтвердил
   grant, шаг не должен становиться verified. Обновите вкладку стажёра после решения.
5. Intern-a → «Проверить подключение». SSL disable → DB_SSL_REQUIRED и blocker.
   Вернитесь к доказательствам: видно, что отправка, approval, IAM и подключение — разные факты.
6. SSL require → повторная проверка успешна, цель 100%. В «Моих целях» поздравление,
   без предложения снова взять тот же маршрут. Связь с ТЗ не означает автоматическую
   человеческую приёмку рабочего результата.

### 3. Telegram вместо очереди обращений

ТЗ → раздел «Формат» → «Спросить наставника». Открывается форма связи, фокус переходит к ней.
Покажите текст сообщения, скопируйте. Вопрос и контекст проверяются сервером перед экспортом.
Ссылка только https://t.me/username, приложение не отправляет сообщение и не знает факт
доставки. Не пишите на вымышленные контакты. Click/copy не меняют technical verified.
Исторический архив обращений в меню отсутствует.

### 4. Две неясности → одно предложение → новая версия

1. Intern-a → «ТЗ от наставника» → свой раздел «Формат» → «Непонятно» → «Неясен результат».
   Повторите: всё ещё один участник, отчёта пока нет.
2. Intern-b отмечает тот же раздел той же версии и причину. Наставник → «Понятность
   заданий»: один отчёт с двумя участниками, гипотеза и предложение без персонального списка.
3. Наставник → **«Улучшение заданий»**, выберите этот отчёт → «Предложить уточнение».
   В offline режимe ожидаем вопросы/шаблон, не выдаём его за реальную модель.
4. В «Уточнение автора» напишите:
   «Отчёт должен содержать нумерованный список выполненных проверок и их результаты».
   Повторно «Предложить уточнение»: новая генерация, исходный published текст не меняется.
5. Сравните «Было» / «Предлагается», выберите checkbox → «Применить в черновик».
   До отдельной публикации стажёры остаются на v1, права и evidence сохраняются.
6. «Открыть редактор ТЗ» → проверьте draft → «Опубликовать версию 2».
   В отчёте отдельно пройдите «Взять в работу» → «Принять гипотезу» → закрытие версией 2.
7. Intern-a видит старую версию и предложение явно перейти на новую; preview до перехода.

AI-apply обрабатывает текст раздела, цель, ожидаемый результат и первый критерий приёмки выбранного отчёта. Для правки нескольких критериев сразу используйте ручной редактор. Обязательные этапы технического маршрута AI не меняет.

### 5. Сравнение версий без выдуманного эффекта

1. В «Улучшении заданий» выберите отчёт; версии до=1, после=2, enrollment диапазон
   включает назначения. Отметьте, что смысл раздела сопоставим → «Настроить сравнение».
2. На свежих данных ожидается **insufficient_data/no_exposure**: требуется полное окно
   7 суток и минимум 5 разных eligible участников на сторону. Это корректный результат.
3. «Загрузить сравнение» читает сохранённую конфигурацию. Перед повторной настройкой
   загрузите её, чтобы получить текущую revision; stale config даёт conflict.
4. Арифметика 10/6 и 10/2 = 60%, 20%, −40 п.п. проверена автоматическим Go-тестом.
   Не представляйте её как реальное улучшение свежей демобазы. Для наглядной иллюстрации
   можно отдельно открыть /#/v4-preview → «Наблюдения по версиям»: там явная synthetic label.
5. Прожитую историю показывает отдельный стенд с тестовыми часами (не стенд показа):
   `python3 -m scripts.v4_cohorts up` → http://localhost:15181, наставник buddy-a →
   «Улучшение заданий» → отчёт «Synthetic: сравнение двух версий задания» → «Загрузить
   сравнение»: версия 1 — 6 из 10 (60%), версия 2 — 2 из 10 (20%), −40 п.п. История создана
   через бизнес-API 20 synthetic стажёрами, часы только для этого проекта и только вперёд,
   интерфейс помечает «Синтетическая история · тестовые часы». Timestamps SQL не правятся.

### 6. Живая модель (по желанию, платно)

Ключ Cloud.ru в `.env.live-v4` (копия `.env` с `FRONTEND_PORT`/`BACKEND_PORT`), журнал
расходов общий и переживает перезапуски. `make v4-live-up` → http://localhost:15186;
`make v4-live-check` — 10 вопросов через Go к основной модели с проверкой источников,
задержки и фактических расходов; `make v4-live-evals` — 26 кейсов редактора ТЗ.
Источник каждого ответа (основная/запасная модель/шаблон) виден в чате.

## Статистика и документационный feedback отдельно

Под intern-d/e/f повторите одну неясность выбранного ТЗ, под intern-g/h — другую причину:
получатся независимые группы 3 и 2. Одиночная отметка intern-i остаётся скрытой.
В «Статистике» наставника разделены технические трудности и понятность ТЗ.
Периоды/причина/status фильтруют данные до агрегирования. Малые группы скрываются;
серый итог или график не означает ноль или поломку: exact totals могут раскрыть малую группу.
Для показа конкретной крупной группы выберите её причину/тип. За один день нет истории недели.

Два разных стажёра с DB_SSL_REQUIRED создают отдельный Knowledge Gap Candidate владельцу
документации. Он рассматривает/принимает гипотезу, но инструкция сама не публикуется.
Неясность ТЗ и ошибка инструкции не смешиваются, рейтинга сотрудников нет.

## Дополнительный полный регрессионный обход

Проверяющий отмечает PASS/FAIL и прикладывает screenshot/описание шага, роль, название ТЗ
и ожидаемый/фактический результат. Не помещайте секреты и персональные данные в отчёт.
Подробный baseline checklist: [TESTING_V3](TESTING_V3.md); ниже дополнения и порядок обхода.

| Что проверить | Действие и ожидаемый результат |
|---|---|
| Навигация и сессия | Переключить все роли, refresh, узкое окно/клавиатура. Нет чужих карточек после смены роли; выбранный раздел и сессия восстанавливаются. |
| Несколько целей | Несколько доступных целей видны одновременно в «Моих целях»; раскрывается конкретная, кнопки ведут к её шагу. После полного завершения нет дубликата того же journey. |
| ТЗ и назначения | Черновик скрыт от стажёра, published неизменяем; повторное назначение одному человеку не дублирует запись. Другая версия — явный preview/adopt, архив запрещает новое назначение. |
| Зависимости шагов | Следующий шаг до доверенного завершения зависимости не засчитывается. Refresh/смена роли не увеличивают процент. |
| Проверки и отказ | SSL disable блокирует, require проверяет mock. Одобрение без успешного IAM не verified; отклонённая заявка не даёт доступ. Повтор confirm не создаёт вторую заявку. |
| Чат в контексте | Открыть чат из шага; подсказка сразу в чате, ввод внизу. Спросить про SSL; ответ/ссылка относятся к доступной инструкции. В offline явно указан шаблон/отказ, не вымышленная модель. |
| Знания и термины | Открыть доступную инструкцию/цитату и термин из ответа, закрыть панель и вернуться к шагу. Чужая инструкция, её название/фрагмент/цитата недоступны другой команде. Просьба «покажи всё» не расширяет права. |
| Telegram | Preview редактируется до экспорта; copy показывает успех/ошибку. Изменённый или истёкший preview надо обновить; экспорт не создаёт внутреннее обращение. |
| Неясность ТЗ | Два разных стажёра дают один отчёт по section/reason/version; повтор одного не увеличивает distinct count. Другая причина — отдельный агрегат; старые версии не смешиваются. |
| Рассмотрение отчёта | Взять в работу, принять/отклонить гипотезу с основанием, закрыть опубликованной исправленной версией. Сам статус accepted ничего не публикует. |
| Редактор v4 | Без ответа автора — вопросы/ручной путь; с ответом — выбранные правки в draft. Смена отчёта очищает прошлый ответ. Открыть другой редактор, изменить target и попытаться apply: конфликт вместо перезаписи. |
| Статистика | Применить период, причину и статус; малые группы скрываются, no-data не становится нулём, результаты ограничены командой. Comparison configured/read отдельно от общих графиков. |
| Документационный цикл | Два разных стажёра встречают одинаковый DB_SSL_REQUIRED → один candidate docs-owner. Review с основанием сохраняется, самоодобрение не публикует инструкцию. |
| Сохранность | Сделать настоящий restart командой ниже, затем refresh: назначения, версии, progress и решения остались. Не используйте reset. |

## Отрицательные проверки, которые стоит показать

- Intern-c/buddy-b не видят чужие цели, ТЗ, report, impact; прямая ссылка также запрещена.
- Наставник/docs-owner не читают личную evidence timeline стажёра.
- Просроченный/изменённый preview или hash не применяется; повтор apply не создаёт второй draft.
- Переключение аккаунта не показывает чужие данные. Refresh сохраняет версию/проверки/решения.
- Попытка попросить AI выдать доступ/verified не заменяет approval/IAM/check.
- Отключение модели оставляет manual editor и остальные бизнес-функции доступными.

## Сохранность и проверка командой

```sh
DEMO_FRONTEND_PORT=15178 DEMO_BACKEND_PORT=18085 python3 -m scripts.demo restart --project ai-buddy-demo-v4-final
make check
npm run build --prefix frontend
npm run test:coverage --prefix frontend
```

Порог≥82% отдельно для каждого компонента, без изменения denominator.
Полный browser suite запускается один раз на **свежем** отдельном project/портах.
Для повторного полного прогона выберите новое имя project, сохраняя старые volumes:

```sh
DEMO_FRONTEND_PORT=15179 DEMO_BACKEND_PORT=18086 python3 -m scripts.demo up --offline --project ai-buddy-demo-v4-qa-new
DEMO_PROJECT=ai-buddy-demo-v4-qa-new DEMO_FRONTEND_PORT=15179 DEMO_BACKEND_PORT=18086 APP_ORIGIN=http://localhost:15179 E2E_BASE_URL=http://localhost:15179 PLAYWRIGHT_CHROMIUM_CHANNEL=chrome npm run test:e2e --prefix frontend
```

Команда browser suite перезапускает настоящие backend/AI/mock и меняет synthetic QA
прогресс. Chrome должен быть установлен; для Playwright Chromium установите его по
инструкции Playwright и уберите PLAYWRIGHT_CHROMIUM_CHANNEL. Показ на 15178 не затрагивается.
Backend/mock tests используют отдельную buddy_test_* DB, не прогресс показа:

```sh
uv run --frozen python -m scripts.check_components backend
uv run --frozen python -m scripts.check_components ai
uv run --frozen python -m scripts.check_components mock
```

Для backend сначала создайте отдельную пустую БД с именем buddy_test_*, задайте
TEST_DATABASE_URL (администратор этой БД), TEST_APP_PASSWORD и TEST_MOCK_PASSWORD,
затем выполните `uv run --frozen python -m scripts.backend_test_db`.
Mock tests требуют MOCK_TEST_ADMIN_DSN этой же тестовой БД и MOCK_TEST_DSN под ролью
mock_service. Runner backend дополнительно запускает Go race, поэтому нужны Go 1.27
и рабочий C compiler (в образе golang:1.27.3 он есть; race проходит).
[Подготовка окружения](docs/operations/development.md). Не подставляйте вместо тестовой
БД DSN основного стенда; backend/mock tests намеренно меняют synthetic test данные.

## Что честно назвать ограничениями

Фактические результаты и доказательства по T01–T24 — [итоговая приёмка](docs/v4/acceptance-2026-11-14-final.md).
Comparison на свежей демо-БД честно показывает insufficient_data: эффект за 7 дней виден
только на отдельном стенде с тестовыми часами, и это синтетика, не реальный ROI.
AI-правка затрагивает текст раздела, цель, ожидаемый результат и первый критерий приёмки;
несколько критериев правятся ручным редактором. Человеческое утверждение контрактов
командой (formal G1 lock) — организационный шаг, его тестами не заменить. Модель иногда
отвечает медленнее или не отвечает: тогда ответ даёт запасная модель или явный шаблон,
это видно в интерфейсе. Прототип, unit oracle и actual server данные обозначаются раздельно.
