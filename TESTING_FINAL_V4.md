# Полная проверка финальной локальной v4

Актуальный live-стенд: **http://localhost:15180**. Здесь Go вызывает настоящую
**GigaChat/GigaChat-3-Pro**, резерв — **ai-sage/GigaChat3.5-432B-A28B**;
эмбеддинги — **BAAI/bge-m3**. Корпоративные IAM/БД остаются отдельным синтетическим
сервисом. Настоящая LLM не означает подключение к производственной корпоративной БД.

Статистика с подготовленной историей: **http://localhost:15181**. Это отдельная БД,
20 синтетических участников и явно подписанные тестовые часы. Открывайте её в отдельном
приватном окне: cookie localhost разделяется между портами; после смены стенда войдите заново.
Fixtures и ссылка на прототип убраны из сайта. Старая закладка `/#/v4-preview`
открывает реальное рабочее пространство роли. Тестовые fixtures остались только для unit-тестов.

Для выступления используйте [сценарий защиты](JURY_DEMO_V4.md), для публикации —
[инструкцию переноса в main](MAIN_RELEASE.md).

## 1. Запуск и проверка реальной модели

Из корня feature/tl-v4, при запущенном Docker Desktop:

```sh
make v4-live-preflight
make v4-live-up
make v4-live-budget
```

Ключ и остальные настройки лежат в локальном `.env.live-v4` (права 600, файл исключён
из Git и Docker context). Не копируйте его в отчёты. На другой машине подготовьте этот
файл по `.env.example`: LLM_MODE=live, LLM_PROVIDER=openai, endpoint Cloud.ru,
имена моделей выше, ключ, тарифы, разные FRONTEND_PORT/BACKEND_PORT (15180/18087).
Для первой сборки без готовых локальных image-cache: `make v4-live-up V4_CACHED_BUILD=`.
Preflight проверяет каталог бесплатно; это ещё не тест генерации.

Текущий лимит учёта — **20 ₽**, постоянный том `ai-buddy_ai-budget`.
Повторный запуск сохраняет расходы; неизвестный usage сохраняет резерв.
После текущей приёмки учтено около 14,13 ₽ из 20 ₽ (включая неизвестный резерв).
Перед повторением всех paid-evals проверьте остаток. При необходимости владелец может
изменить LLM_BUDGET_STOP_RUB в локальном файле в пределах своего бюджета (runner допускает
не более 800 ₽) и пересоздать сервисы через `make v4-live-up`; журнал не удаляется.
При лимите модель честно становится недоступной. Не удаляйте журнал/volumes ради повторения.
Тарифы primary: 73,03/176,39 ₽ за млн входных/выходных токенов; резервной модели:
96,22/288,60; embeddings: 0,61. [Каталог провайдера](https://cloud.ru/products/evolution-ai-factory/catalog-foundation-models).

```sh
make v4-live-check
```

Это десять **реальных** последовательных запросов через Go, интервал не меньше 13 секунд
сохраняет серверный лимит 5 запусков/минуту. Используется дополнительный аккаунт intern-i:
не переключайте его параллельно в браузере. После предыдущего прогона подождите минуту.
Проверяются completed run, origin primary/complete, разрешённые источники с повторным
чтением через Go, первый текст ≤20 с, завершение ≤90 с, usage и фактическая цена с
correlation_id этого run. Secondary/offline/неизвестный usage не засчитываются за primary.
Итог: `.cache/v4-live-acceptance.json`; никаких ключей, cookie или текстов переписки.
`--count 1` у модуля — короткая диагностика, она не закрывает десятизапросную приёмку.

Сайт работает через Go API; переключателя Fixtures больше нет. Проверьте у ответа
метку основной/резервной модели: наличие «Live API» само по себе не доказывает вызов LLM.
Прочитайте ответы вручную: ссылки открываются, объяснение соответствует инструкции,
модель не придумывает права, сроки или факт завершения проверки.

## 2. Основной сценарий стажёра и проверка доступа

1. Выберите «Стажёр» (intern-a). «Мои цели» → начните доступный DB-маршрут, если его нет.
   Несколько назначенных целей видны одновременно; подзадачи раскрываются независимо.
2. Откройте «Проверить доступ». В чате спросите про заявку. Ответ/предложение действия
   не меняют progress. Проверьте цель, ресурс, роль и текст preview; подтвердите заявку.
3. «Мои заявки» показывает submitted. Повторное подтверждение не создаёт вторую заявку.
4. Согласующий → одобрите заявку с основанием. Go сам делает свежую IAM-проверку;
   **именно её evidence** засчитывает шаг. Обновите вкладку стажёра.
5. «Проверить подключение»: SSL disable → DB_SSL_REQUIRED/blocker; SSL require → успех.
   Следующий шаг до проверенной зависимости не должен засчитываться.
6. «Мои цели»: 100%, поздравление, без предложения пройти тот же маршрут заново.
7. «Почему такой статус?»/«Подзадачи и доказательства»: отправка, одобрение, IAM и
   проверка подключения — разные факты. Старое отозванное evidence не заменяет текущий статус.

У уже завершившего маршрут аккаунта используйте другого дополнительного стажёра.
Старые данные не сбрасывайте. Проверки корпоративного mock — настоящие вызовы отдельного
процесса и сохранение PostgreSQL, но не реальные корпоративные права.

## 3. Задания наставника и связь с техническими целями

1. Наставник buddy-a → «Мои задания» → «Новое ТЗ». Назовите его уникально, заполните цель,
   раздел «Формат», ожидаемый результат и критерий приёмки; сохраните черновик.
2. Стажёр не видит draft. Опубликуйте v1 и назначьте intern-a и intern-b.
   Повторное назначение одному человеку не создаёт дубль.
3. «Улучшение заданий» → раскройте «Дополнительно: технические цели назначений». У нужного назначения отметьте «Для этого назначения нужен доступ к БД команды A» → «Добавить цель доступа к БД». Для ТЗ без работы с БД этот шаг пропустите.
   Разрешение маршрута не выдаёт доступ к БД.
4. Intern-a → «Задания и цели» → выбранное ТЗ → «Связать с технической целью» →
   preview → confirm. Без разрешения автора связь отклоняется. Existing journey используется повторно.
5. «Открыть ТЗ» показывает pinned версию. Выполнение технической цели не означает
   человеческую приёмку результата ТЗ. Несвязанные задания и цели остаются видны.

## 4. Вопрос наставнику через Telegram

ТЗ стажёра → раздел → «Спросить наставника»: форма раскрывается, фокус переходит к ней.
Отредактируйте вопрос, создайте preview, проверьте разрешённый контекст, скопируйте текст.
Экспорт не отправляет сообщение и не подтверждает доставку. Отправка в Telegram вручную.
Не отправляйте сообщения на вымышленные демонстрационные контакты.
Изменённый/просроченный preview требует обновления. Исторического inbox/архива обращений нет.

## 5. Как замечания стажёров превращаются в улучшенное ТЗ

### Зачем нужен этот сценарий

Он помогает найти формулировку, на которой спотыкаются несколько новичков, и исправить
её для следующей группы. Стажёр отмечает конкретную непонятную часть задания, Go
считает разных участников, AI предлагает редакцию, а наставник решает, что менять.
Это работа с **текстом ТЗ**. Она не выдаёт доступ к БД и не засчитывает техническую цель.

### Подготовьте один понятный пример

Под наставником создайте новое ТЗ «Отчёт о проверке подключения — демонстрация»:

- Цель: «Подготовить отчёт о выполненных проверках».
- Заголовок раздела: «Формат»; текст: **«Опишите результат в свободной форме»**.
- Ожидаемый результат: «Отчёт о проверке подключения».
- Критерий: «В отчёте перечислены выполненные проверки».

Сохраните черновик, опубликуйте версию 1 и назначьте **это же ТЗ** intern-a и intern-b.
Для этого сценария добавлять цель доступа к БД не обязательно: мы проверяем ясность ТЗ.
Используйте новое название для каждой репетиции, чтобы не путать старые отчёты.

### А. Два стажёра сообщают об одной проблеме

1. Выберите intern-a → «ТЗ от наставника» → созданное ТЗ → раздел «Формат».
2. Нажмите «Непонятно», выберите **«Неясен результат»**, затем «Отметить».
   Смысл отметки: «я не понимаю, что именно должен содержать мой отчёт».
3. Повторная отметка intern-a не считается вторым человеком. Переключитесь на intern-b
   и повторите отметку в **том же разделе той же версии**, с **той же причиной**.
4. Наставник → «Понятность заданий»: появился один отчёт о повторившемся затруднении.
   Видны ТЗ, версия, раздел, причина и число участников. Персонального списка отметивших нет.

Если отчёта нет, проверьте совпадение ТЗ/версии/раздела/причины и что использованы два
разных аккаунта одной команды. Вопрос в Telegram сам по себе такой отметкой не является.

### Б. Наставник получает предложение AI

1. Откройте «Улучшение заданий». В «Отчёт о неясности» выберите созданное ТЗ,
   раздел «Формат», **v1**. Карточка под выбором показывает, с каким контекстом вы работаете.
2. Нажмите «Предложить уточнение». На время ожидания появится статус генерации.
   Сохранённый текст ТЗ от этого не меняется.
3. Модель может предложить новый текст либо спросить недостающие требования. Вопрос —
   корректный результат: AI не должен сам придумывать, что вы хотите получить от стажёра.
4. В «Уточнение автора» введите: **«Отчёт должен содержать нумерованный список выполненных
   проверок и их результаты»**, затем повторите «Предложить уточнение».
5. Прочитайте «Было», «Предлагается» и «Почему/Обоснование». Проверьте, что не появились
   придуманные сроки, системы, доступы или новые обязательные условия.
   Метка «Ответ модели» означает LLM; «Шаблон без LLM» — честно обозначенный запасной путь.

### В. Применение и публикация — два разных решения

1. Отметьте флажком подходящую правку → «Применить в черновик».
2. Убедитесь, что сообщение говорит о сохранении **черновика**, а не о публикации.
3. Нажмите «Открыть редактор ТЗ», проверьте новую формулировку, при необходимости
   отредактируйте её и нажмите **«Опубликовать версию 2»**.
4. Только теперь новая версия опубликована. Стажёры с назначенной v1 продолжают видеть v1:
   откройте задание стажёра, просмотрите предложение перехода и подтвердите принятие v2.
   Это защищает работающего человека от внезапной замены условий.

Если правка не подходит — «Отклонить предложение» или обычный ручной редактор.
Отчёт старой версии после публикации остаётся доступным для истории/сравнения;
для новой AI-правки нужен отчёт текущей версии. Конфликт после параллельного изменения
ТЗ требует нового предложения: AI не должен перезаписывать чужую свежую редакцию.

### Г. Закройте цикл рассмотрения

В «Понятности заданий» откройте исходный отчёт. Последовательно выберите «Взять в работу»,
«Принять гипотезу», затем закройте отчёт исправленной опубликованной v2 с основанием.
«Принять гипотезу» означает согласие с проблемой текста, а не публикацию и не приёмку
работы стажёра. Для сравнения новых групп используйте раздел 6.

| Что сделали | Что действительно изменилось |
|---|---|
| Отметили «Непонятно» | Зарегистрирован сигнал по разделу; выполнение цели не меняется |
| Запросили AI-предложение | Получен вариант текста; ТЗ не меняется |
| Применили выбранную правку | Изменился черновик; назначенная v1 прежняя |
| Опубликовали v2 | Новая версия доступна для назначения/явного перехода |
| Стажёр перешёл на v2 | Его назначение теперь использует новые условия |
| Закрыли отчёт версией 2 | Зафиксировано решение наставника по проблеме |

Автоматическая правка отчёта по критериям ограничена первым существующим критерием;
остальные доступны в обычном редакторе. Дополнительный платный набор проверок AI:
`make v4-live-evals` → `.cache/v4-revision-live.md`. Перед повтором проверьте бюджет.

## 6. Сравнение версий и графики

На свежем live-стенде семидневной истории может не быть: «Недостаточно данных» корректно.
Нужно ≥5 eligible участников каждой версии, полное окно 7 суток и принятые contributions.
Малые numerator/complement скрываются вместе с производными числами; no-data не является нулём.

Для полного наглядного теста:

```sh
make v4-cohorts
```

Откройте http://localhost:15181 в отдельном приватном окне → наставник → «Улучшение заданий» →
отчёт `Synthetic: сравнение двух версий задания · Формат · v1` → «Загрузить сравнение».
Ожидание: **6/10 = 60%, 2/10 = 20%, −40,0 п.п.**; видна подпись синтетических тестовых часов.
Это серверный расчёт по созданным через бизнес-API данным, не UI-фикстура и не реальный
измеренный эффект продукта. Повтор `make v4-cohorts` сохраняет сценарий.

«Статистика» → «Понятность моих ТЗ»: проверьте графики, период, причину и состояние отчёта.
В «Дополнительных участниках» этого стенда есть 20 cohort-аккаунтов. Технические трудности
и понятность ТЗ считаются отдельно. Нет рейтинга сотрудников или доказанной причинности.

## 7. Документационный feedback и знания

- Повторите DB_SSL_REQUIRED под двумя разными стажёрами. Docs-owner получает один
  Knowledge Gap Candidate по journey/step/error, а не по неясности ТЗ.
- Рассмотрите candidate, примите/отклоните гипотезу с основанием. Решение сохраняется;
  инструкция не публикуется автоматически.
- В чате откройте цитату, инструкцию и термин; возврат к шагу сохраняет контекст.
  Чужой документ команды B не должен раскрывать заголовок, текст или цитату.

## 8. Доступ, ошибки, интерфейс и сохранность

| Проверка | Ожидаемый результат |
|---|---|
| intern-c / buddy-b по прямой чужой ссылке | отказ без чужого текста/названия |
| Наставник/docs-owner открывают личную timeline | отказ; только разрешённый handoff snapshot |
| Prompt injection просит выдать доступ/verified | права и progress не меняются |
| Смена аккаунта / refresh | прежние чужие карточки не остаются на экране |
| 390px, Tab/Enter, collapse, длинный чат | элементы доступны, ввод не исчезает, горизонтального переполнения нет |
| Provider/schema/timeout/budget failure | честная метка secondary/offline/unavailable; ручные бизнес-действия доступны |
| Повтор preview/confirm/apply | нет дубля заявки/черновика, stale возвращает конфликт |
| Малые группы / неизвестная история | скрытие или insufficient_data; не выдуманный ноль |

Fake auth/429/timeout/cancel/budget/cooldown сценарии покрыты unit tests; они не являются
наблюдавшимися авариями Cloud.ru. Не расходуйте весь бюджет и не меняйте ключ ради демонстрации отказа.

```sh
make v4-live-budget
make v4-live-restart
make v4-live-budget
```

После перезапуска refresh: назначения, draft/published, progress и решения сохраняются;
журнал расходов не обнуляется. Порог и неизвестные резервы остаются прежними.

## 9. Автоматическая проверка командой

```sh
make check
npm run build --prefix frontend
npm run test:coverage --prefix frontend
uv run --frozen python -m scripts.check_components ai
```

Backend/mock checks запускайте только с отдельной подготовленной `buddy_test_*` БД,
как описано в [DEFENSE_V4](DEFENSE_V4.md). Они меняют тестовые данные. Порог ≥82% отдельно
для Go, AI, mock и FE, без исключения бизнес-кода. Go race требует C compiler.
Полный browser suite — на свежем изолированном project, не на данных показа:

```sh
DEMO_FRONTEND_PORT=15183 DEMO_BACKEND_PORT=18090 python3 -m scripts.demo up --offline --project ai-buddy-demo-v4-teamcheck-new
DEMO_PROJECT=ai-buddy-demo-v4-teamcheck-new DEMO_FRONTEND_PORT=15183 DEMO_BACKEND_PORT=18090 APP_ORIGIN=http://localhost:15183 E2E_BASE_URL=http://localhost:15183 PLAYWRIGHT_CHROMIUM_CHANNEL=chrome npm run test:e2e --prefix frontend
```

Для повторного полного прогона используйте новое имя project; не удаляйте старые volumes.
Отдельная browser-проверка готовых когорт:

```sh
E2E_COHORT_DATASET=1 E2E_BASE_URL=http://localhost:15181 PLAYWRIGHT_CHROMIUM_CHANNEL=chrome npm run test:e2e --prefix frontend -- v4-cohort-operator
```

Фиксируйте роль, шаги, ожидаемый/фактический результат и screenshot. Не добавляйте ключи,
cookie или личные данные в баг-репорты. Локальная проверка не заменяет cold build,
публикуемый CI и независимое утверждение полного release/контрактов.
